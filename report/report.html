1. Problem and who it is for

Facts about Thailand's 77 provinces are scattered across long Wikipedia articles (history, landmarks, festivals, name meanings) and a separate statistics table (population, area, density, region). Students, travellers and teachers often need one checkable fact, e.g. "Which Northern province is the most densely populated?" or "What is the population of the province with the Bridge over the River Kwai?". A plain chatbot answers these confidently but often wrongly. Our closed-book baseline (the same model with no tools) invented a "Tawin Lake" as Thailand's largest lake and claimed Bangkok is the only province with over a million people (the true count is 21). The Thai Province Agent answers from two grounded sources and shows its evidence: numbered Wikipedia citations for prose facts, and the SQL query plus result rows for numbers.

The corpus (77 province articles plus the "Provinces of Thailand" table, joined with the six-region grouping) is outside the reference app's domain. It is committed to the repository together with a fetch script (scripts/fetch_corpus.py).

2. Design

Figure 1. Architecture. The HTTP layer (main.py) only frames requests and SSE events. The logic lives in agent.py and rag.py. Data access lives in tools.py, retrieval.py and sqldb.py. llm.py is the only module that calls a model, which lets 48 tests run offline with a fake model.

Structured output + schema validationEvery agent turn must be one JSON object validated by a Pydantic discriminated union on action (search_docs | run_sql | calculator | final_answer). The proxy ignores response_format, so we extract the first balanced JSON object, validate it, and on failure send the validation error back for one repair turn. Answers cite [n], and the final answer's citation numbers are checked against the sources actually retrieved; invented numbers are dropped and counted.

Agent loop with tools (agentic)A loop of call → validate → run tool → feed back the result. Stop conditions: a final answer, max 6 steps, an identical repeated call, or two invalid turns in a row (each followed by one forced final turn, then a safe fallback). The model must call at least one tool before answering. Tool results are clipped and framed as untrusted data.
Text-to-SQL (advanced, agentic)Ranking and aggregate questions can't be answered by retrieval (no chunk says "the 21 provinces over one million"), so the agent writes SQL. Four guards apply: a single SELECT/WITH statement with a keyword deny-list, a read-only connection (mode=ro), an SQLite authorizer allowing only reads of the provinces table, and a step limit plus a 50-row cap. The calculator parses with ast against an allow-list and never uses eval.
Served interfaceFastAPI POST /api/ask streams Server-Sent Events. The UI shows each tool call, SQL result tables, the answer and clickable citations live. There is also a single-shot "Quick RAG" mode with token streaming.

Everything evaluated runs at temperature=0. The configuration (models, retriever, top_k, min_score) and secrets come from environment variables, and .env is git-ignored.

3. Evaluation design

3.1 Test sets (hand-built from the corpus)

  • Retrieval set: 43 queries, each labelled with (article, evidence span), e.g. "Where is the highest mountain in Thailand?" → chiang-mai, evidence "Doi Inthanon". 30 are implicit (the province is not named) and 13 are explicit. A chunk counts as relevant if it comes from the labelled article and contains the evidence span, so the same labels score every chunking fairly. Each query has one answer-bearing passage, so Recall@k equals Hit@k. There are also 12 off-corpus queries for the min_score floor.
  • Answer set: 34 questions: 14 text (from articles), 11 sql (from the table), 7 multi-hop (both, sometimes with arithmetic) and 2 unanswerable (the correct behaviour is to refuse). Gold answers for sql and multi-hop items were computed from the CSV, not typed by hand.

3.2 Metrics and baselines

Retrieval: Recall@1/3/5 and MRR@10. Baselines: naive fixed 200-word chunks with no header and no boilerplate removal, plus each chunking idea ablated. Answers: deterministic accuracy. An answer is correct if it contains a gold alias, or a number within the item's tolerance (e.g. ±1%). Unanswerable items count as correct only for a refusal. We then read every answer marked correct and overrode false positives (listed with reasons in eval/data/manual_audit.jsonl), and we report both the automatic and the audited score. Baselines: the closed-book model (no retrieval, no tools) and single-shot RAG (top-5 retrieval, cited answer, no tools).

What could and couldn't be measured. Midway through the evaluation, the class proxy's embedding endpoint began failing every request ("401 … column t.tpd_limit does not exist", a proxy-side database error) or timing out, for over an hour. All 1,851 chunk embeddings were built before the outage, but the query embeddings needed for the dense and hybrid evaluation could not be obtained. All retrieval and RAG/agent numbers below therefore use BM25 retrieval, and the shipped default (RETRIEVER=bm25) matches what was measured. The dense/hybrid path and the min_score sweep are implemented and unit-tested; python -m eval.eval_retrieval produces those numbers from the cache once the endpoint works. The server also degrades to BM25 automatically when embeddings fail.

The agent beats both baselines by a margin larger than the uncertainty: audited accuracy is 0.941 vs 0.500 (single-shot RAG) vs 0.294 (closed-book), and the confidence intervals don't overlap. The per-type breakdown shows where the gain comes from. Retrieval fixes text questions (closed-book 4/14 → RAG 12/14), but RAG can't do sql (2/11) or multi-hop (1/7). No passage contains "the total population of the Southern region", so RAG correctly says "the sources don't say". The agent routes these to SQL (11/11) and chains search_docs → run_sql → calculator for multi-hop (7/7), e.g. "How many times larger is the province containing Doi Inthanon than Phuket?" → search finds Chiang Mai, SQL returns 22,311 and 547 km², and the calculator gives 40.79. This costs latency (median 2.2 s vs 0.4 s) and 1.29 tool calls per question. The model followed the JSON protocol well: one repair in 34 runs, and no invented citation numbers.

5. Failure analysis

Failure 1: retrieval vocabulary mismatch (agent, t05). "What does the name Phitsanulok mean?" The answer is in the article's first chunk, written as lit. 'Vishnu's realm', with no word "mean" or "name". BM25 instead ranks the Toponymy sections of Chonburi, Samut Songkhram and Nakhon Sawan first, because those sections contain "name" and "meaning". The agent repeated the identical search, the repeated-call stop fired, and the forced final turn honestly answered "I could not find the meaning…". This is the right behaviour (no hallucination) but a miss. It is exactly the paraphrase case dense embeddings target, and the first thing to re-measure once the embedding endpoint returns.
Failure 2: a correct-looking number that is wrong (agent, t12), caught only by auditing. Asked for the size of Kaeng Krachan National Park, the agent wrote that Phetchaburi province "has an area of 2,915 km²" and the park covers "approximately 1,457.5 km²", having misread "covers nearly half of the province" and then used the calculator on that misreading. In fact the park is 2,915 km². Our number matcher found "2,915" and scored it correct, so the automatic accuracy (0.971) overstated the agent; the audited score is 0.941. A similar hedged RAG answer (two conflicting areas for Nakhon Ratchasima) was also overridden. Lesson: number-contains metrics need a claim-level check (or an LLM judge with a rubric) for numeric questions.
Failure 3: the baselines. Closed-book answers are fluent and wrong on numbers: "Bangkok is the only province exceeding one million" (true: 21), Phuket "approximately 400,000" (table: 430,000), the newest province is "Mueang Khlong" (it is Bueng Kan, created 2011). Single-shot RAG got 15 of the 18 sql/multi-hop items wrong. 9 of those 15 were explicit refusals ("the sources don't say"), which is a safe failure. The rest show a subtler problem: answering a table question from prose. Phuket's population came back as "360,905 at the end of 2012" (a stale figure in the article), and "the densest Northern province" came back as Phitsanulok, the only density figure among the retrieved chunks. Routing these to SQL is what fixes them.

Where the evaluation is weak. (i) The two unanswerable items don't separate the systems: even closed-book refuses them, so refusal quality needs a larger adversarial set. (ii) 34 and 43 items are small; the intervals above are wide for the baselines. (iii) I wrote both the questions and the labels, from the same corpus, so phrasing may favour lexical retrieval; held-out questions from other people would be a fairer test. (iv) The table is one snapshot (registered population, Dec 2024), while article text sometimes quotes other figures. Bangkok's article says 9.1 M (metro estimate) vs the table's 5.46 M registered.

6. Limitations and next steps

  • Measure dense and hybrid retrieval (already implemented) and pick min_score from the in-corpus vs off-corpus sweep once the proxy's embedding endpoint is stable. Then re-run the agent with hybrid retrieval, starting with t05.
  • Better numeric scoring: check that the number is attached to the right entity (claim-level), or add an LLM-as-judge from a different model family with a fixed rubric, calibrated against the manual audit.
  • Bigger, independent test sets: about 100 questions written by people other than the author, more unanswerable and adversarial questions (e.g. prompt-injection text placed inside an article), and Thai-language questions (the BM25 tokenizer currently ignores Thai script).
  • Robustness: the proxy produced intermittent spurious 401s even when healthy. The client retries with backoff, the embedding cache persists batch by batch, and serving falls back to BM25. A local embedding model would remove this single point of failure.
